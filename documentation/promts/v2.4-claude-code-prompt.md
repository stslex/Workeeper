## Implementation order

Follow **Section 6 of the spec verbatim**. Each numbered step is a
checkpoint: finish it, run the relevant module tests, only then move on.
Do not jump ahead.

The order is dependency-driven, not user-visible-first:

- Tokens (step 1) before everything else — every later component reads them.
- Set-type label fix (step 2) is a tiny touch — group with tokens in
  the same commit if convenient.
- New kit components (step 3) before data layer and screen rework that
  consume them.
- Data layer queries (step 4) before list-screen rework that surfaces them.
- **PlanEditorScreen (step 5) before LiveWorkoutScreen (step 10)** — live
  workout depends on navigating into the new screen instead of opening
  a sheet.
- List screens (steps 6, 7) before detail screens (8, 9) so the row
  pattern is locked when detail-screen work begins.
- Live workout (step 10) is the heaviest single step — bring it in only
  after kit primitives, plan editor screen, and list/detail patterns are
  stable.
- Chart fixes (11) and templates picker (12) are isolated; either order
  after step 10 is fine.
- Spacing migration (step 13) is **opportunistic**, not a separate final
  pass — touch a file in steps 5–12, migrate its `AppDimension.Padding`
  callsites, done.

## Spike before committing step 3.3

Before committing `ReorderableLazyColumn` in step 3.3, validate nested
LazyColumn behavior on a throwaway test screen. Section 9 of the spec
calls this out as the highest implementation risk.

Specifically: outer `LazyColumn` (live workout exercises) containing an
inner `LazyColumn` (sets per exercise). Confirm Compose does not throw

If unstable: fall back to non-lazy `Column` rendering for the inner sets
list. Set count per exercise is bounded (typically ≤10), so no
performance concern. Document the choice in `tech-debt.md` if you take
the fallback.

## Locked behaviors / watchouts

These are not negotiable. If implementation pressure pushes you toward
violating one of them, escalate (don't quietly bypass).

- **PlanUpdateRule on reorder** (spec 5.4 + Section 9). Reorder is
  positional permutation, not size change. Verify that the existing
  `PlanUpdateRule.apply()` is **not** triggered on reorder paths. If it
  is, add a `reorderOnly: Boolean` flag or a separate `reorderPlan(...)`
  interactor method. Do not rewrite the rule.
- **Snackbar undo collision** (spec 5.4, Section 9). If a user deletes
  a second set while the first snackbar is visible, **replace** policy:
  only one undo at a time, the new snackbar overrides the previous (and
  the previous deletion commits immediately). Do not stack snackbars.
- **`AppDimension.Padding` migration** (spec B1, step 13). Opportunistic
  only. Do not grep-replace the codebase. Touch a file → migrate its
  Padding callsites → commit together. Untouched files keep their
  `@Deprecated` warnings until a future stage cleans up.
- **Light theme is untouched** (spec A2). Do not modify
  `provideLightAppColors()`. Only `provideDarkAppColors().accent` and
  `accentTintedBackground`/`accentTintedForeground` for dark are tuned.
- **No schema migration** (spec Non-goals). No new migration files in
  `core/database/migrations/`. No `ALTER TABLE`. Only new `SELECT`
  queries (F1, F2). If a step seems to need a schema change, you have
  gone off-spec.
- **`SelectionTopBar.kt` and `BulkActionBar.kt` are deleted** (spec C1,
  C2). Do not refactor them — delete the files and their callsites
  in `AllExercisesScreen.kt` and the trainings analogue.
- **`AppSwipeAction` stays in kit** (spec module map). It is removed
  only from list features, not from the kit module — other features may
  use it later.
- **Set-type chip rendering is already correct** (spec D6). Do not edit
  `AppSetTypeChip.kt`. Wrap call sites in `AppTooltip` only.
- **Set-type label fix** (D8): one-line change to `SetTypeUiModel.DROP`'s
  `labelRes` argument plus removing `tools:ignore` from the string
  resource. No enum changes, no migration.

## Commit and PR conventions

- Conventional commits: `feat(v2.4): ...`, `refactor(v2.4): ...`,
  `test(v2.4): ...`, `chore(v2.4): ...`.
- One logical step per commit (Section 6 numbered steps map roughly to
  commits; step 5 PlanEditorScreen and step 10 LiveWorkout may need
  multiple commits each).
- Open the PR as draft after step 5; mark ready after step 13 + final
  test pass.

PR title: `feat(v2.4): design foundation refactor`

PR body sections:
- **What** — bullets from spec Section 1 (in-scope).
- **Why** — link to the planning conversation in Claude Project + cite
  the spec.
- **Touched modules** — table from spec Section 3.
- **Schema migrations** — None (state explicitly).
- **Tests added** — list per spec Section 8.
- **Out of scope** — bullets from spec Section 1 (non-goals).
- **Tech debt** — link to `tech-debt.md` updates.
- **Risks accepted** — copy from spec Section 9 with the mitigation
  outcome (which path was taken on the reorderable spike, etc.).

## When to stop and ask

Escalate back to the planning context (do not improvise) if:
- A locked decision in the spec contradicts what the existing code
  requires (likely means the spec has a gap).
- The reorderable spike fails on the nested LazyColumn case AND the
  non-lazy fallback also breaks (escalate before redesigning).
- A new DAO query (F1 or F2) requires a schema change to be efficient.
  Do not add a migration without confirmation.
- Tech-debt accumulates beyond the in-scope register (more than 2 new
  🟡 or any 🔴 not anticipated by the spec).

Otherwise: follow the spec, follow the order, run the tests, ship.
